# Watched links follow change notifications, and poll only where there are none

Task SPEC-8. Amends ADR 0016's watch mode (story 57): how a `LinkWatch` learns that a watched link's sources changed.

## Context

A watched intaker listed all its sources every second (`watch_interval_s` 1.0, one `scandir` pass in `watch_intaker`) and compared the listing with the last one. On a folder of 100,000 files that pass takes about a third of a second of Python, so the watcher held about a fifth of a core (and the GIL of the GUI process) for as long as the folder was watched, with nothing arriving. A resolve running beside it slowed down too: an arrival took about 7 s to land as a collection, where the resolve alone takes about 2 s. On a network drive each pass is a full remote directory walk every second.

## Decision

1. **A watcher kind may register a `WatchListing` beside its watcher** (`register_watcher(kind, fn, listing=factory)`). It names the folders to observe (`roots`), and updates the watcher's table in place for the paths a change notice names (`apply`), giving the same table a full listing would. The intaker's is `specto_intake.watch_listing.IntakerListing`: a path that is a file now is stat'ed and kept by the walk's rules (pattern, depth, symlinked folders only when the source follows links, `.specto/` never); a folder now is walked; a path gone is dropped with everything under it, through a folder index so that costs the folder's own entries. A notice for a source root itself asks for a full listing. On a case-insensitive file system (probed on the source folder) a notice's name is checked against the folder's own entry names, so a rename that only changes case moves the entry (a change) instead of adding one and removing the other later; on a case-sensitive one names are compared as they are. Writers' temporaries (a dotfile ending `.tmp` or `.part`, as atomic writers leave while writing) are left out of the table and ignored as notices: the rename into place is the arrival. The listing also does the full listing (`full`) and says whether a source is missing (`source_missing`), so the runtime never reads the kind's table format.
2. **Notifications come from watchdog** (Apache-2.0; ReadDirectoryChangesW on Windows, inotify on Linux, FSEvents on macOS), wrapped in `specto_core.fswatch.Notifier`. One observer serves the process, with one watch per folder however many links follow it; each notice fans out to the notifiers subscribed to that folder. The subscriber list is replaced, never changed in place, and dispatch reads it without the hub's lock: watchdog dispatches holding its observer's lock, which scheduling and unscheduling take too (an unschedule also joins the emitter thread, with no timeout, and a Windows emitter can hang in its close). So the hub's lock guards the hub's own state only and is never held across a watchdog call: each folder watch has a state, `arming` while a subscriber schedules it outside the lock, `armed`, and `reaping` while it is unscheduled outside the lock, and a subscriber for a folder whose watch is arming or reaping waits for that to end (`ARM_TIMEOUT_S`, 10 s, then it is refused and its link polls until the backoff's retry). watchdog keys its emitters by (path, recursive), so a schedule during a teardown would otherwise be handed the emitter being stopped. A folder nobody follows keeps its watch for 5 s (`LINGER_S`) before a reaper, on a timer, marks it reaping and unschedules it, so a watch toggled off and on reuses it, and a watch is never stopped just after it started (watchdog's Windows emitter can then block in a read issued after its cancel). Every schedule and unschedule (a subscriber arming a folder, the reaper, a subscriber tearing down a watch whose notices stopped or whose folder was replaced) runs on a helper thread waited for `WATCHDOG_CALL_TIMEOUT_S` (2 s): one that never returns holds the observer's lock for good (an unschedule joins the emitter with no timeout; a schedule then waits for that lock), so that observer is given up in the same lock hold that drops the watch, its watches with it (their links poll with the reason and try again on the backoff), the subscriber is refused, and the next subscriber starts a fresh observer. A given-up observer's emitter threads run on, their handles open, until the process exits. The hub shuts down at the process's exit and in the test sweep, bounded at about `STOP_TIMEOUT_S` (1 s) in all: while it runs the hub is closed, an arm in flight is undone and refused, a waiter woken is refused rather than starting a new observer; the exit's shutdown leaves it closed. A folder's own "modified" notice is dropped; both ends of a move are applied. Only those three backends count: watchdog's polling and kqueue fallbacks do not (kqueue opens every file).
3. **The watcher lists everything once, then applies notices.** Its baseline listing comes first, at once, so it is as close as can be to the resolve's own listing (SPEC-83: notifications take a while to arm, the observer starts on first use, and a baseline taken after them swallowed every file that landed meanwhile, so the resolve never showed it and no notice ever named it); it then starts notifications and lists once more when they are armed, so what changed while they armed is reported too. It gathers notices until they have been quiet for 50 ms (at most 0.5 s) before applying them. The runtime's `link.arrivals`, its debounce and the resolve are unchanged, so the status line ("N arrived, resolving") and undo (an arrival is no undo step) behave as before; tests check both in notify mode. (Nothing sets the gallery's `newCount`, the "+N new" pill, today; nothing here changes that.)
4. **A full listing still runs, as a safety net**: every 30 s, and never closer than 50 listing durations, so a slow listing stays a small share of a core; on a network drive every 10 to 30 s, never more than 30 s apart whatever the listing takes. A storm of notices (1,000 paths or more in one batch, an agent writing a folder full) is applied as it comes, and one full listing follows once it has been quiet for 2 s (an overflow inside it loses notices), never closer than 50 listing durations to the last; a storm that goes on is listed after 5 s, then at doubling gaps up to 60 s. A batch naming more than half the table is listed instead of applied. Lost-notice reports are handled the same way: watchdog drops a ReadDirectoryChangesW overflow silently (the call returns no bytes), and Specto's observer subclasses its emitter to report it.
5. **A watched folder renamed or replaced is armed again.** A handle follows the folder it was opened on, so after a rename the watch would report the old folder's changes. The watcher checks each root's identity (device and file id, plus the creation time on Windows) every second; on a mismatch it arms the path again and lists once, or polls when the path is gone.
6. **A drive that accepts the watch and sends nothing is polled.** When two safety-net listings in a row find changes no notice reported, the watcher polls with the reason "this drive sends no change notices".
7. **Where notifications are not to be trusted, the watcher polls as before and says so.** That is no native backend, a source that is not there yet (tried again after each listing), notifications that would not start (inotify's watch limit), that stop (a share refusing them, the folder deleted) or that never come (decision 6), and network file systems on Linux and macOS (NFS, SMB, sshfs and the like), where the kernel sees only this machine's changes. A Windows network drive keeps notifications, because the SMB server sends them for every client's changes, plus the shorter safety-net interval. Notifications that stopped, were refused or never came are tried again after 30 s, then at doubling gaps up to 5 minutes, so a share that blipped is followed by notices again once it holds; notifications that held for 5 minutes reset the gap. The watcher's `mode` (`notify` or `poll`) and `reason` show in `links.watch_status`. The event `link.watching` fires when a watcher settles on its mode and whenever the mode changes. The status bar says "auto-update on (polling: ...)" for a view fed by a polling watcher. `SPECTO_WATCH=poll` forces polling everywhere.
8. **Folders reached through links send no notices.** A symbolic link or a junction inside a watched folder (followed when the source follows links; Windows walks junctions either way) has no watch of its own. The full listing records them, and the status says they are covered by the periodic listing only ("N folders reached through links covered by the periodic listing only").
9. **The resolve is not incremental.** An arrival still re-runs the whole intaker on a worker (ADR 0016 note), about 2 s for 100,000 files. Making grouping incremental is a separate change.

## Measured (`tools/bench_watch.py`, a 100,000-file folder in 100 subfolders, Windows, NTFS, warm)

| | Idle CPU (share of one core) | Full listings in 20 s idle | Arrival noticed | Arrival's collection landed |
|---|---|---|---|---|
| Before (poll every 1 s) | 21.5 % | 15 | 0.81 s | 7.0 s |
| After (notifications) | 0.2 % | 0 | 0.63 s | 2.6 s |
| After, over SMB (`\\localhost\C$`) | 0.2 % | 0 | 0.62 s | 2.8 s |
| `SPECTO_WATCH=poll`, over SMB | 23.7 % | 13 | 1.28 s | 3.6 s |

"Arrival noticed" is `link.arrivals`, which turns the view's status to "1 arrived, resolving". The 0.5 s of it is the runtime's debounce. Over 65 s idle with notifications the process used 0.3 % of a core, safety-net listings included.

## Consequences

- A new runtime dependency, watchdog (pinned below 7: 7.0 shipped days before this change).
- Specto's Windows observer depends on watchdog internals: `winapi.read_directory_changes`, `winapi._parse_event_buffer` and `winapi.WinAPINativeEvent`, checked when the observer class is built, and the emitter's `_whandle`, checked as it reads. If one moves, it uses watchdog's own observer (or the stock read), without the lost-notice report; the 30 s listing still catches what an overflow loses.
- Dropbox and similar sync clients write into an ordinary local folder (a temporary file, then a rename into place). The rename's notice names the file, so it arrives as one file.
- The file tree's own auto-update (ADR 0022 decision 7) still relists its loaded folders every interval. That is cheap, since it covers only open folders, and is unchanged.
