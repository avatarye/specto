# Spike S1 (shell-deciding half) + S2: Qt Quick on the OpenGL RHI from PySide6

> Historical record, not instructions: the branches, paths and tools named below are from the M1/M2 spikes and have moved or been retired.

Date: 2026-10-12. Branch `m1/spike-s1-s2`, code under `spikes/s1_s2/`.
Scope per HLD section 10 (`shell` decision): WebEngine under the OpenGL backend,
a `TextureItem` showing a native GL texture rendered on the render thread, a
buildable native module loadable from PySide6, plus the three S2 API checks.
Storm is not part of this run; a spinning shaded torus drawn with raw GL stands in.

## Verdict: PASS, with one design rule

| HLD 5.5 criterion | Result | Evidence (run name in `spikes/s1_s2/results/`) |
|---|---|---|
| 60 Hz at 1920x1080, native texture beside WebEngine | 60.0 fps item, 60.0 fps window swap (min 59.9) | `gui_native_web` |
| GUI thread > 80 % idle | 98.3 % idle (1.7 % CPU busy); 82.7 % in the worst case, Python pushing 8.3 MB frames at 60 Hz | `gui_native_web`, `gui_pyframe_web` |
| No WebEngine regression under OpenGL RHI | WebGL2 60.0 fps (min 60.0) and Monaco 20.5 edits/s, same as the D3D11 baseline (60.0 / 20.6) | `gui_native_web` vs `d3d11_web_baseline` |
| Frame-copy cost if the texture is not shared | 1080p RGBA upload on the render thread: 0.46 ms CPU + 0.59 ms GPU; Python handoff adds 2.6 ms GUI-thread per frame | `gui_upload_web`, `gui_pyframe_web` |
| S2: `QSGTexture` from native | `QNativeInterface::QSGOpenGLTexture::fromNative` wraps the FBO texture, works | `native/textureitem.cpp` |
| S2: C++ `QQuickItem` usable from PySide6 | QML plugin loads in the PySide6 process; Python reads and writes its properties | `tests/test_native_module.py` |
| S2: `QWebEngineUrlSchemeHandler` with range requests | Works, with two rules (below) | `gui_native_web` `web.range` |

**The design rule.** A C++ item must not re-arm frames from the render thread
(`QQuickWindow::update()` called inside the render callback, which is the
`QQuickFramebufferObject::Renderer::update()` pattern). Under the threaded render
loop with vsync on the OpenGL backend that pattern starves the GUI-thread sync:
WebEngine drops to 15.7 fps and GUI timers stall for 60 ms at a time while CPU
sits idle (`gl_native_web`). Driving frames from the GUI thread (one
`item.update()` per frame, here a QML `FrameAnimation`; in the app the frame
source's "new frame" notification posted to the GUI thread) removes the stall
completely (`gui_native_web`). `StormItem`/`MpvItem`/`TextureItem` in `_spectoqt`
follow the GUI-driven form; HLD 4.1 "the update callback only posts to the render
thread" for mpv becomes "posts to the GUI thread, which calls `update()`".

Reasons this is a pass and not a partial: every number is at or above the bar on
the GUI-driven path, the WebEngine number equals the D3D11 baseline, and the
failing path is a pattern we control, not a platform limit. The Storm half of S1
(HLD section 10) still decides in-process `StormItem` vs frame source later.

## Extension mechanism: how native Qt Quick items reach PySide6

Chosen: **a C++ QML module plugin built against the Qt SDK that matches the
wheel's Qt version, loaded by QML import.** No shiboken.

Why it is the least painful path:

- The PySide6 wheel ships Qt DLLs, `pyside6.abi3.lib` and the shiboken headers,
  but **no Qt headers and no Qt import libs**. Any C++ item needs the SDK
  regardless of the binding route; aqtinstall puts the matching one in place in
  ~30 s (three archives, 430 MB).
- Same major and minor version is enough for the plugin to load; same patch is
  what we pin (`build.py` refuses to build if `qVersion()` differs from the SDK).
  At runtime the plugin's `Qt6Core.dll`/`Qt6Quick.dll` imports resolve to the
  copies PySide6 already loaded into the process, by module name.
- `qt_add_qml_module(... PLUGIN_TARGET spectospike)` produces one DLL plus
  `qmldir` and `.qmltypes`. Python does `engine.addImportPath("<dir>/qml")`, QML
  does `import Specto.Spike`. Build is 14 Ninja steps, 20 s.
- Python sees the item as `QQuickItem` (nearest known base; `metaObject().className()`
  is `TextureItem`). Properties go through `property()`/`setProperty()`, methods
  through `QMetaObject.invokeMethod(obj, "resetStats", Qt.DirectConnection)`,
  signals through the meta-object. That covers everything `specto-app` needs:
  Python configures items, items never call Python.

Shiboken bindings (the HLD 4.1 wording) stay available if a Python-side API with
real types is ever needed: `shiboken6_generator` 6.12.0 exists on PyPI and needs
libclang plus a typesystem XML. Cost is a day of build plumbing and a second
artifact to keep in step with the wheel, for no M1 benefit. The HLD's
"shiboken-wrapped" should read "QML module plugin, shiboken optional".

Gotchas met on the way (each costs an hour if unknown):

- A QML `property alias tex: tex` read from Python fails with
  `RuntimeError: Can't find converter for 'TextureItem*'`. Use `objectName` and
  `window.findChild(QQuickItem, "tex")`.
- `cmd.exe /c "call vcvars64.bat && cmake ..."` cannot be quoted correctly from
  `subprocess` with paths containing spaces; `build.py` writes a throwaway `.bat`.
- Qt 6 no longer raises the Windows timer resolution. Without
  `winmm.timeBeginPeriod(1)` a 4 ms `QTimer` fires every 15.6 ms
  (`gl_native_web_no_timer_period`: 100 % idle because nothing runs). `app.py`
  sets it; `specto-app` must too if any Python tick is under 16 ms.

## What was built

- `native/textureitem.{h,cpp}`: `TextureItem : QQuickItem` with a `TextureNode :
  QSGSimpleTextureNode` living on the render thread. The node owns a
  `QOpenGLFramebufferObject`, a GLSL 330 program and a torus mesh (200 k triangles
  by default, 2 M in one run). It renders in a `QQuickWindow::beforeRendering`
  slot (direct connection, render thread) between `beginExternalCommands()` and
  `endExternalCommands()`, exactly where `QQuickFramebufferObject` does it, and
  wraps the FBO's colour texture once with `QSGOpenGLTexture::fromNative`.
  Render-thread counters (frames, CPU ns, GPU ns via `QOpenGLTimerQuery`,
  sync ns, bytes uploaded) are published as Q_PROPERTYs every 500 ms.
  Three modes: 0 native mesh (zero copy), 1 `glTexSubImage2D` of a synthetic
  RGBA frame every frame (render-thread upload cost), 2 the same with a frame
  Python pushed into the `frame` property from `multiprocessing.shared_memory`.
  Two drive styles: `continuous` (render thread calls `window->update()` after
  each frame) and GUI-driven (`item.update()` per frame from QML/Python).
- `main.qml`: Calm Canvas-ish cards: `WebEngineView` left, `TextureItem` right,
  stats overlay, a rotating rectangle so a stalled scene graph is visible.
- `app.py`: PySide6 host. Registers `specto://`, initialises WebEngine Quick,
  sets `QSG_RHI_BACKEND`, loads the QML, then measures on the GUI thread:
  `time.thread_time()` for CPU busy (idle % = 100 - busy), a 4 ms precise
  `QTimer` for scheduling latency (p50/p95/max), `frameSwapped` queued to the GUI
  thread for window fps, item properties for render-thread numbers, and the page
  title (JSON the page republishes every 500 ms) for WebGL fps, Monaco edits/s and
  range-request results. Warm-up 5 s, measure 10 s, one JSON per run.
- `scheme.py`: `QWebEngineUrlSchemeHandler` serving `web/` and a 32 MB
  `blob.bin` where byte i == i & 0xff, so the page can verify slices.
- `web/index.html` + `webgl.js`: 4 000 instanced cubes in WebGL2 at
  `requestAnimationFrame` rate, Monaco with a 6 000-line JSON model edited 20
  times a second with `revealLineInCenter` every tenth edit, range-request probes.
- `run_matrix.py`: the matrix below; `tests/`: 20 pytest cases (range parsing,
  path traversal, module metadata, plugin instantiation from PySide6 offscreen).

## Measurements

All windows 1920x1080 logical, DPR 1.0, 10 s measurement after 5 s warm-up.
`item fps` is the render-thread frame count of `TextureItem`; `swap fps` is the
window's `frameSwapped` rate; `timer` is the lateness of a 4 ms GUI-thread timer.
Full table: `spikes/s1_s2/results/summary.md`; per-run JSON beside it.

The timer p95 of ~11 ms is one frame: in the threaded render loop the GUI thread
blocks during each sync while the render thread runs `updatePaintNode`. It is a
latency floor for GUI-thread work, not CPU use (p50 is 0.02 ms), and it is the
same with or without the web view and with or without the native item. The D3D11
backend shows p95 1.0 ms because its render thread does not block on vsync
inside the sync window; on OpenGL with `--swap-interval 0` the p95 is 1.1 ms as
well (`gl_native_web_swap0`), confirming the cause is the vsync wait.

At 120 Hz the 3.55 ms "draw CPU" is the driver blocking in a GL call to pace to
vsync (GPU time 0.16 ms, same mesh as the 0.12 ms case); it lives on the render
thread and costs the GUI thread nothing.

What the extra runs rule out: not the mesh cost (12 triangles fails the same),
not GPU contention (2 M triangles passes on the GUI-driven path), not a
cross-adapter issue (Chromium's unmasked renderer is the RTX in every run, and
pinning it with `--use-adapter-luid` changes nothing: `x_gl_s1_nv`), not Chromium
vsync (`--disable-gpu-vsync`: `x_gl_s1_nochromevsync`, still 15 fps). It is the
render thread re-arming itself while blocked on vsync, which only lets the GUI
thread's sync (WebEngine delivers its frames through it) in every fourth frame.
Without vsync (`swap0`) or with the basic loop (everything on the GUI thread, 71 %
idle: fails the idle bar) the stall is gone; at 120 Hz the GUI thread is blocked
~12 ms every tick instead (p50 11.7 ms), the same mechanism at a different rate.

### Frame-copy cost (HLD 4.5, CPU frames in shared memory for M1-M2)

| Path | Where | Cost per 1920x1080 RGBA frame (8.3 MB) |
|---|---|---|
| Texture shared in-process (mode 0) | - | 0 |
| `glTexSubImage2D` from a CPU buffer (mode 1) | render thread | 0.46 ms CPU, 0.59 ms GPU |
| Python: `shm.buf[...].tobytes()` then `QByteArray(bytes)` then `setProperty("frame")` (mode 2) | GUI thread | 2.64 ms mean, 4.1 ms p95 (two 8.3 MB copies), 17 % of the GUI thread at 60 Hz |
| Python: `setProperty("frame", bytes)` directly | GUI thread | 0.93 ms (one copy) plus the `tobytes()` copy |

PySide6 6.12.0 rejects `QByteArray(memoryview)` with `ValueError` even though its
stub lists `memoryview` (checked with `shm.buf`, slices, `.cast("B")`,
`.toreadonly()` and a plain `memoryview(bytearray)`), so the zero-copy handoff
from shared memory is not available from Python. For M1-M2 the frame-source
path should hand `_spectoqt` the shared-memory **name and offset** and let the
item map it and upload on the render thread (mode 1 cost: 0.46 ms CPU, no GUI
thread involvement). Python pushing bytes works but spends 17 % of the GUI thread
on one 1080p30-60 stream; two streams would break the 80 % bar.

### Scheme handler and range requests (S2)

Measured on `blob.bin` (32 MiB) through `specto://app/`:

| Request | Result |
|---|---|
| `fetch` with `Range: bytes=1048576-2097151`, handler replies the full file via `QFile` | 206, 1 048 576 bytes, bytes verified, `Content-Range: bytes 1048576-2097151/33554432` set by Chromium, 54 ms |
| suffix range `bytes=-16` | 206, 16 bytes |
| 1 KiB at offset 0 / at the end of the file | 1.5 ms / 80 ms: Chromium streams from byte 0 and discards, O(offset) |
| `blob.bin?range=33553408-33554431`, handler serves only the slice (200) | 1.7-2.3 ms, bytes verified, `X-Specto-Range` header visible |
| full 32 MiB `fetch` | 160-370 ms, 90-200 MB/s through the `QFile` stream |

Rules that fall out:

1. Chromium applies the `Range` header itself on top of a full reply. A handler
   that answers a Range-carrying request with a **partial** `QBuffer` crashes the
   process (access violation in the GUI process, no Python traceback); this was
   first misread as a `requestHeaders()` crash and bisected to the partial body.
   `requestHeaders()` itself is fine.
2. Because the built-in slicing is O(offset), large-file reads (rosbag chunks,
   LiDAR tiles) use an app-controlled `?range=` URL and a 200 with the slice.
   `<video>` elements, which need true 206 semantics, stay on `MpvItem` (S5).
3. `QWebEngineUrlScheme` needs `FetchApiAllowed` or `fetch()`/XHR fail with
   "Failed to fetch"; `CorsEnabled` lets Monaco's `data:` workers `importScripts`
   from the scheme; a worker base URL must be absolute (standard Monaco CDN recipe).
4. `setAdditionalResponseHeaders` is `QMultiMap<QByteArray, QByteArray>` in C++;
   PySide6 iterates each dict value, so a bare `QByteArray` value becomes one
   header value per character (`Accept-Ranges: s, e, t, y, b`). Pass lists.
5. Parent the reply device to the job (`dev.setParent(job)`). Releasing it from a
   Python `job.destroyed.connect(lambda ...)` instead crashes under load.

## Consequences for M1

- Keep Qt Quick on `QSG_RHI_BACKEND=opengl` (HLD 5.5 default stands).
- `_spectoqt` is a QML module plugin (`import Specto.Native`) built by a
  `build.py` like this one against the aqt SDK pinned to the wheel's Qt; add the
  version check to CI. Shiboken is not needed for M1.
- Item rule: native items request frames from the GUI thread (`update()`), never
  by `QQuickWindow::update()` from the render thread. mpv's render-update callback
  and Storm's frame-ready notification post to the GUI thread.
- Frame sources deliver shared-memory handles to `_spectoqt`, not bytes to Python.
- Web panels: scheme handler serves full bodies for Range requests, `?range=` for
  app-side slicing, lists for response headers, `FetchApiAllowed | CorsEnabled`.
- `specto-app` calls `timeBeginPeriod(1)` on Windows at startup.
- Budget a one-frame (11 ms) GUI-thread latency floor from the threaded render
  loop sync when sizing channel ticks and command latency targets.
